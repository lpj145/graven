## Fairness notes
- **Reused contexts.** zidl uses `SimplePool`. FlatBuffers uses `FlatBufferBuilder::reset()`
  and a reused offsets vector. Cap'n Proto uses a reused `ScratchSpaceHeapAllocator`.
- **Cap'n Proto writing.** The output is `serialize::write_message` into a reused `Vec`,
  which includes a copy of the segments. Without that copy (a writev of the segments) it
  would be a little faster.
- **Lists in Cap'n Proto.** Cap'n Proto needs to know the list's size before writing it. The
  `zidl` column in `bank` uses a **streaming list**, the hard path. The `zidl_known` column
  uses a known count, comparable to Cap'n Proto.
- **"Unverified" reading:**
  - FlatBuffers: `root_unchecked`.
  - Cap'n Proto: `traversal_limit = None`. It still checks bounds, because Cap'n Proto
    always does.
  - zidl: `read()`, which validates required fields and checks bounds on every access.
- **"Verified" reading:**
  - FlatBuffers: `root()`, with the full verifier.
  - Cap'n Proto: the default `ReaderOptions`. Its verification is lazy, so it changes almost
    nothing.
  - zidl: a full `verify()` followed by `read_all`.
- **Strings.** zidl **validates UTF-8** on every string read. FlatBuffers `root_unchecked`
  and Cap'n Proto `as_bytes()` do not. There is no measured `_unchecked` variant yet (see
  next steps).
- **Optionals.** FlatBuffers omits scalars equal to the default, which favors it in size
  when there are zeros. Cap'n Proto has no optional scalars; we use `union { none; value }`.

## Verdict per criterion (spec §8)

| criterion | result |
|---|---|
| **Win on size** | ✅ against FlatBuffers and **unpacked** Cap'n Proto in every scenario: 20–50% smaller than FlatBuffers and 3–40% smaller than Cap'n Proto for small and medium messages. For 64 KiB blobs the difference is negligible (~0.03%). ❌ **Packed** Cap'n Proto is smaller in `bank/*`, `frame/10` and telemetry without humidity, paying CPU to pack and unpack. |
| **Zero allocations per message** | ✅ 0 in every scenario, including with a streaming list. With messages in flight, < 0.05 per message (see the condition above). FlatBuffers also has 0; Cap'n Proto has 1. |
| **Win on writing** | ❌ **Does not win.** Against FlatBuffers: loses for messages of 1 element or smaller (bank/1 streaming 1.9× slower, telemetry 2.5×, chunk/64 2.9×); wins for larger lists (bank/10: 1.5× streaming and 2.2× known; bank/100: 2.1× and 3.6×; frame: 3.1–6.7×) and for 64 KiB blobs (1.6×). Against Cap'n Proto: loses on lists (1.8–3.2×) and on tiny messages; wins only on 64 KiB blobs (2.6×). |
| **Tie or win on reading** | ⚠️ **Mixed.** Wins on telemetry, chunk and frame/10. Loses on `bank` to FlatBuffers and Cap'n Proto (UTF-8 validation) and on frame/500 to Cap'n Proto (≈ 12%). Reading one field it loses to FlatBuffers (≈ 2.5×) and beats Cap'n Proto (≈ 5×). With verification it beats FlatBuffers in every scenario, by 1.6× (bank/1) to 4.1× (frame/500). |

## Hypotheses for the losses (to validate in the next round)

1. **Fixed write overhead (~30 ns).**
   - Likely cause: `SimplePool` takes a `Mutex` twice per message (`take` and `give`). Add
     `reserve` and `split().freeze()`.
   - Next step: measure with a thread-local pool, or reuse the `Builder` itself.
2. **Writing lists is slower than Cap'n Proto.**
   - Likely causes: every `set` goes through `fixed_buf()` (a match), plus a bounds check and
     `set_bit`. `push` uses `resize` with a zero-fill per element. With streaming, add the
     final memcpy and the pointer fix-up.
   - Cap'n Proto does one memset of the whole list and then only stores.
   - Next steps: zero the list in one block, `set` without a redundant bounds check, and
     specialize `TableW` for "fixed part in the main buffer".
3. **`read()` costs ~4 ns more than `root_unchecked`.**
   - Cause: `check_required` walks the `Req` list. Spec §4.3.1 asks for an `AND` with a
     precomputed mask; that **was not implemented in this phase**.
   - In lists, `from_ref` validates the required fields of **every element** (frame/500 = 500
     validations).
   - Next steps: a mask per byte of bits, and validating elements once per list when
     `elem_fixed_len` covers the reader's layout.
4. **Strings in `bank`.**
   - Cause: zidl validates UTF-8 and the others do not.
   - Next step: measure the `str_unchecked` variant and/or validate UTF-8 only in `verify()`.
5. **The "no alignment" hypothesis did not turn out to be a problem.**
   - In the scalar scenarios (telemetry, chunk, frame/10) zidl reads faster than both.
   - The read losses come from validation (items 3 and 4), not from unaligned access.
