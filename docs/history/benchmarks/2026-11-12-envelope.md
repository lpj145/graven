## The envelope

An envelope is `[20 B header][message][4 B CRC32C]`: **+24 bytes** per message. The header
carries the magic, the version, the schema id and the size. The CRC32C covers the header and
the message.

- **Writing:** `Builder::new_enveloped` reserves 20 bytes before each message.
  `flush_envelope(schema_id)` fills the header in place, computes the CRC and returns a
  `Bytes`. The message is not copied.
- **Reading:** `X::from_bytes(buf)` decodes the envelope (checks the magic, version, size
  **and CRC**), checks the schema id and runs the full verification. It is equivalent to
  `X::verified(payload)` plus the cost of the envelope.

## Cost of the envelope (ns, median)

`write_owned` is the fair comparison line: one owned `Bytes` per message (`flush()`), the
same contract as `flush_envelope()`. In `bank/10` both use a list with a known count.

### Writing

| scenario | write_owned | write_enveloped | abs overhead | rel overhead |
|---|---:|---:|---:|---:|
| telemetry | 22.4 | 32.9 | +10.5 | +47% |
| chunk/64 | 27.2 | 40.9 | +13.7 | +50% |
| chunk/65536 | 1602.6 | 2630.2 | +1027.7 | +64% |
| bank/10 | 72.5 | 109.8 | +37.3 | +51% |

The overhead is dominated by the CRC (`crc32c` of ~60 B costs ~6 ns, of 64 KiB ~1.65 µs, see
below) plus writing the 20 B header. In chunk/65536 the extra cost (1.03 µs) is smaller than
the bare CRC (1.65 µs): probably because the owned 64 KiB write already spends time in
`memcpy` and the CRC overlaps part of it (not verified).

| read | ns |
|---|---:|

Reading the result:
- **The extra cost of reading is the CRC**: zidl's full verification does not touch the data
  bytes (`chunk/65536` verifies in 4.9 ns), but the CRC walks the whole message. That is why
  the overhead grows with size: ~10 ns for messages of tens of bytes, 1.7 µs for 64 KiB.
- For small messages the envelope costs 10 to 14 ns per side (writing and reading). In
  exchange you get integrity (CRC32C), a version and a schema check.
- For large payloads the cost is proportional to size, at ~40 GB/s (below): 1 µs per ~40 KB.

### CRC32C throughput

`zidl::crc32c` (hardware acceleration, the SSE4.2 `crc32` instruction) against `crc32c_sw`
(slicing-by-8, used without `std`).

| size | hw (ns) | hw GB/s | sw (ns) | sw GB/s |
|---|---:|---:|---:|---:|
| 64 B | 6.06 | 10.6 | 11.9 | 5.4 |
| 1 KiB | 30.2 | 33.9 | 349 | 2.9 |
| 64 KiB | 1645 | **39.8** | 23460 | 2.8 |

GB/s = 10⁹ bytes/s (criterion reports GiB/s: 37.1 GiB/s at 64 KiB). The hardware path is
~14× faster than the software one for large messages.

## The deferred regression series (Tasks 4 and 5)

Context:
- **Task 4** changed `Builder::begin_msg` (a prefix of 4 or 20 bytes). The ±5% write
  comparison was inconclusive because of machine load.
- **Task 5** changed the trusted/verified read path of `bank`.

Since the machine's absolute speed may differ from round 2, there are controls:
1. **Absolute value** against the round 2 table (column "Δ abs").
2. **Ratio** zidl/fbs and zidl/capnp against the round 2 ratio (cancels differences in
   machine speed). A real regression is a ratio deviation > ~5–8% above the noise.
3. **Direct A/B.** The plan's snapshots (`snaps/t1-base` = the pre-plan code, `t4-*`,
   `t5-base`) were built with the same `rustc` and measured **interleaved with the current
   code**, in the same session. This is more reliable than comparing with a table from
   another day.

In this round the absolute FlatBuffers and Cap'n Proto numbers stayed within ~±5% of round 2
for writing (fbs bank/1 58 vs 56.8; frame/500 17.7 µs vs 17.7 µs) and ~+5–10% for reading.
That is, the machine is close to round 2's, with fbs reads a bit slower.

The tables in this section (up to the verdict) were measured **before** the fix described in
"Fixing the regression"; the verified bank/1 row (56 ns) is the value with the regression.
The final numbers are in the fix section.

## Fixing the regression (verified bank/1)

**Bisection by snapshots** (`read_all_verified/zidl/bank/1`, 3 interleaved runs, ns): t1-base
45.9 · t1-head 54.2–56.4 · t2-base 55 · t3-head 55 · t4-base 54–55 · t4-head 57 · t5-base
56–58 · t5-head 57 · current 58–60. The step of ~+10 ns came in with **Task 1**, which only
touched `Error` (new variants carrying data: `Incomplete { needed: usize }`,
`SchemaMismatch { expected: u64, found: u64 }`, `UnsupportedVersion(u8)`) and the writer's
`list_size`. Tasks 4 and 5 contribute ~+1–2 ns (noise).

**Cause.** With the new variants, `Error` went from 1 byte (an enum without data) to 24
bytes. No `Result<_, Error>` fit in registers anymore. The `verify` functions of the schema
types (`Transaction::verify`, `FromTable::verify` of `Transaction` and `Entry`,
`ListR::verify`) were called out of line (without `#[inline]`), so each message paid for the
call and for returning the `Result<(), Error>` through memory. Evidence from an isolated
experiment (a copy of the code, no repository file touched): with `Error` back at 1 byte the
time drops from 57 to 45 ns (equal to the pre-plan 44); with a 12-byte `Error` (`u32` fields)
it does not change (57). Only `#[inline]` on the `verify` functions, keeping the 24-byte
`Error`, brings the time to 39.5 ns.

**Change.** `#[inline]` on the 11 `verify` functions in
`crates/zidl-schemas/src/{bank,game,iot,stream,lib}.rs` (`FromTable::verify` of each table,
the public `verify` of each root, `ListR::verify`). No change to unsafe code, to `Error` or to
the structure of the views (buildable only via `verify`). Coverage: the existing tests
(`verified.rs`, equivalence, conformance and the required-mask proptest) exercise these same
paths; `cargo test --workspace` still has 174 passing, 0 failing. There was no behavior
change, so no new test was needed.
